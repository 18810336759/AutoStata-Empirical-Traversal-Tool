# AUTOstata 基准检验 2.0：人机协同使用手册

本目录完成主效应、中介效应、调节效应的**基准筛查**及同批次结果整合。程序按用户预设运行并保存可核验的证据；研究者负责数据、理论与识别设计，检查每条结果，决定正式检验和论文如何报告。candidate、strong_pass、weak_pass 是筛查标签，不是因果识别或最终假设证明。

## 一、输入前：用户的责任

1. 先读懂参考文章和研究问题，明确 X、Y、中介 M、调节 W、控制变量的定义、计算公式、单位、方向和时间口径。当前版本不替用户构造变量或选择理论。
2. 在提供数据前，按研究方案完成年份、行业、ST、金融业等适用的样本筛选，保留原始文件和筛选记录；检查企业 ID—年份是否唯一、年份是否真实、合并是否正确、缺失及异常值是否可解释。全局 YAML 的 sample_period 和 sample_rules只是说明与目录标签，需用户自行处理和选择。
3. 至少理解系数、标准误、p值、N、固定效应、聚类标准误、缺失值和控制变量的含义。研究中介还须区分总效应、X→M、控制 X 后 M→Y；研究非线性还须理解平方项、观察范围和拐点。不能仅凭筛查通过或图形直接声称因果或曲线成立。
4. 在看结果前确定合理的处理、控制变量和模型设定，记录选择理由。当前系统统计的是**已执行设定**；候选筛查、抽样枚举和运行限额可能使其他合理设定未被执行。

## 二、改哪里、运行哪个程序

| 步骤 | 用户编辑的文件 | 执行入口 |
| 数据路径、面板列、预处理、控制变量、固定效应、输出和模块开关 | config/analysis_config.yaml | skill/other/config_validation.py 先作只读校验 |
| X→Y、线性／U 型／倒 U 型主效应与筛查规则 | skill/main_effect/main.yaml | skill/main_effect/run_main_effect.py |
| X→M→Y、两步／三步法与路径规则 | skill/mediation_effect/mediation.yaml | skill/mediation_effect/run_mediation_effect.py |
| 被调节关系、W、交互形式与方向预期 | skill/moderation_effect/moderation.yaml | skill/moderation_effect/run_moderation_effect.py |
| 假设登记、逐假设通过门槛、理论链、合并键、综合表和展示案例 | skill/result_synthesis/synthesis.yaml | skill/result_synthesis/run_result_synthesis.py |

# AUTOstata 运行入口与内部文件

日常使用编辑 `config/analysis_config.yaml` 和相应模块目录里的 YAML，然后执行需要的 `run_*.py`。三个效应模块可分别运行；需要整合时，在效应模块完成后运行 `skill/result_synthesis/run_result_synthesis.py`。

| 类型 | 文件 | 是否手动运行 |
| --- | --- | --- |
| 配置预检 | `config_validation.py` | 可选；正式回归前运行一次 |
| 主效应 | `main_effect/run_main_effect.py` | 按需运行 |
| 中介效应 | `mediation_effect/run_mediation_effect.py` | 按需运行 |
| 调节效应 | `moderation_effect/run_moderation_effect.py` | 按需运行 |
| 结果整合 | `result_synthesis/run_result_synthesis.py` | 效应结果完成后运行 |
| 公共组件 | `path_utils.py`、`preprocessing.py`、`result_schema.py`、`_internal/` | 不直接运行，由入口程序调用 |

默认项目输出根目录为 `output/<project.name>/`，可通过全局 YAML 的 `output_settings.output_root` 修改。其中 `run_manifest.json` 记录当前公共批次、各模块运行状态及整合状态。每个模块目录的 `run_record.json` 记录当次运行的配置快照、输入数据指纹、代码与环境版本、预处理定义以及输出文件清单。模块目录中的 `config_snapshot/` 是回归执行时保存的配置；整合目录的 `config_snapshot/<模块名>/` 保存所读取模块的历史快照，`synthesis_input_config.yaml` 则仅记录整合时的全局配置。

结果文件写入临时目录，完成后才替换正式模块目录。当前版本请依次运行模块，避免多个进程同时更新同一项目的批次清单。旧版输出没有运行清单，需用当前版本重新运行对应效应模块，才能纳入受批次校验的整合。


在本目录执行的命令示例：

~~~bash
../../.venv/bin/python skill/other/config_validation.py config/analysis_config.yaml
../../.venv/bin/python skill/main_effect/run_main_effect.py config/analysis_config.yaml
../../.venv/bin/python skill/mediation_effect/run_mediation_effect.py config/analysis_config.yaml
../../.venv/bin/python skill/moderation_effect/run_moderation_effect.py config/analysis_config.yaml
../../.venv/bin/python skill/result_synthesis/run_result_synthesis.py config/analysis_config.yaml
~~~

如果未安装本项目虚拟环境，可把 ../../.venv/bin/python 换成已安装所需依赖的 Python。先确认全局和模块开关；不必运行已关闭模块。不要并发运行同一项目的多个入口，以免同时更新运行清单。

公开演示配置启用三个效应模块及 synthesis；改用自己的研究设定时，以当前全局 YAML 和模块 YAML 的开关为准。不需要的模块可以关闭，但须同时核对 synthesis 模块选择、假设登记及理论链。各假设的编号、变量口径、方向和启用状态仍由研究者确认；程序不会为获得显著结果而自动改动。

## 三、三个模块共同的预处理含义

三个 runner 调用同一个共享预处理引擎，固定顺序是：**原始核心变量有效年份门槛 → 同企业按真实年份插值 → 按分位点缩尾 → 各模型所需变量完整案例筛选**。门槛在插值前计算，按不同真实年份计数。插值不跨企业；内部缺口按年份距离计算，边界方向与允许的最大日历年缺口由全局 YAML 控制。重复企业—年份或非整数年份会阻止不可靠的插值。

缩尾只处理 continuous_variable_settings 中获许可的变量；分位点和范围读取 preprocessing.winsorize，支持 full_sample、by_year、by_industry、by_industry_year。按行业分组需提供行业列。分组键缺失的观测保持原值。基准方案既不插值也不缩尾；插值、缩尾及二者结合的处理方案仅在 treatment_profiles 开启时运行。

**进入处理流程的数据范围与最终估计样本不同。**模型构造好公式后，按它自身所需变量删除缺失行。三个模块以及中介链内不同路径可以有不同观测行和 N；系统分别记录 sample_identity、N、完整案例删除量，并提示差异，不因样本不同自动判失败。处理定义和实际影响保存在 processing_definition_json、processing_trace_json 与 preprocessing_definitions.json，供以后复现代码读取。

## 四、基准筛查如何读，何时需要正式确认

阶段 A/B 使用必选控制变量，在已配置门槛和处理方案中进行基础筛查；各模块依据自己的规则标记 candidate。阶段 C 在配置启用时扩展可选控制变量组合，按相应假设规则给出 strong_pass 和 weak_pass。组合可能只抽样执行，因此结果比例不能被解释为全部合理设定的比例。失败、不显著和方向不符的已尝试结果仍应在完整审计表中查看。

主效应的 U／倒 U 型会构造平方项并做当前配置规定的筛查；平方项显著**不足以证明**曲线在观察区间成立。调节模块能构造线性、二次调节和调节曲线的模型项，并输出相应筛查及可选条件效应数据；曲率项或转折点参考量也不是完整确认。严格 U 型确认、Utest、观察范围与拐点的进一步核查及正式展示图仍需后续补充检验。

中介模块现阶段执行两步法或三步法的**路径回归筛查**，不做 Sobel 或 Bootstrap 间接效应确认。三步法要求总效应时，阶段 C 在相同控制变量组合下重估 X→Y。中介链通过须同一公共设定、同一机制链、所需路径齐全且每条路径分别达到当前规则；一条路径显著不能代表整条链通过。路径样本差异要人工审查。正式论文仍须结合理论、识别与稳健性检验选择和解释模型。

## 五、目录、批次和输出开关

输出路径是 output/<project.name>/<样本说明>/<模块名>/。同一项目同一模块成功重跑会替换其完整输出；更改 project.name 会新建项目目录，旧项目保留。样本说明文字不表示程序按它筛选过数据。运行先在临时位置完成，再发布正式目录；失败不会留下半套新结果，上次完整结果仍在，失败尝试写入运行清单。成功重跑时，上次生成但本次关闭的图表或其他可选文件会清理。

每个项目的 run_manifest.json 记录当前 run_id、公共配置／数据身份、模块状态和 synthesis 状态。数据或公共计算配置变化会开启新批次，旧模块结果不得进入新 synthesis；只变更某模块假设会更新其 module_revision 并使旧 synthesis 失效；同配置重跑模块可复用公共 run_id，但 run_instance_id 更新。每个模块的 run_record.json 保存当次数据指纹、代码／运行环境、配置快照、预处理定义及文件清单。模块 config_snapshot/ 保存的是**回归时** YAML，不是当前磁盘上后来改过的版本。

当前版本核验模块 YAML 的**文件哈希**和运行代码／环境，因此只修改模块 YAML 的注释或更新效应脚本，也可能使旧运行记录不再适用；本次代码更新后，先重跑本轮启用的效应模块，再运行 synthesis。旧输出不能冒充当前配置的结果。

普通 CSV、Excel、原始结果、成功结果和摘要受相应输出开关控制。standardized_results.csv、specification_index.csv、hypothesis_results.csv 是机器衔接产物，有独立开关；关闭机器产物后该模块本次不能进入 synthesis，系统不会读取旧文件代替。

## 六、三个效应共同输出什么

以下文件位于各自的 `main_effect/`、`mediation_effect/`、`moderation_effect/` 目录。人工表受全局普通 CSV／Excel、原始结果／成功结果开关控制；机器衔接 CSV 独立于普通 CSV 开关。空表仍有表头。

| 三模块共有文件 | 一行代表什么；先看什么 |
| --- | --- |
| full_results | 已尝试的回归模型／中介路径，含失败行；看公式、系数和模块诊断 |
| control_combination_results | 已执行的 C 阶段模型／路径，含未通过与失败行 |
| candidate_results | A/B 阶段通过候选条件的一条假设级判定；不是 C 通过 |
| strong_pass_results | C 阶段强通过的一条假设级判定 |
| weak_pass_results | C 阶段至少弱通过的一条假设级判定，**包含强通过** |
| standardized_results.csv | 机器长表，一行一个模型检验项；统一公共列在前，模块诊断列在后 |
| specification_index.csv | 一行一个模型检验项的公式、公共设定、处理和样本索引 |
| hypothesis_results.csv | 各阶段的假设级判定；中介为同设定、同机制链的所需路径汇总 |
| preprocessing_definitions.json、run_record.json、config_snapshot/ | 处理规则、当次运行证据和历史配置 |

前五个同名人工表以 `model_id、specification_id、模块名称、假设编号、假设描述、检验阶段` 起头，随后依次是样本区间／规则／门槛、处理方案、插值／缩尾、控制变量组合及纳入的控制变量、固定效应、聚类标准误、运行状态、候选／强／弱标签和失败原因；模块专属诊断列排在后面。`candidate/strong/weak` 三表的完整表头跨模块一致。`full/control_combination` 的公共列顺序一致，但主效应模型、中介路径和调节模型的专属列及行粒度不同。主效应显式标记 AB／C；中介和调节同样可用“检验阶段”区分。

| 重要字段 | 读法 |
| --- | --- |
| model_id、假设编号、path_type、chain_id、检验项、effect_role | 定位模型、理论假设、机制路径和当前系数；同一模型可有多行检验项 |
| specification_id、控制变量组合ID、样本门槛、处理方案、固定效应设定、聚类标准误设定 | 公共设定身份；相同编号不意味着相同假设或相同最终样本 |
| run_id、run_instance_id、common_fingerprint、data_sha256、module_revision | 批次、模块运行、公共计算／数据及模块版本证据 |
| 模型公式、模型项定义 | 表格可见的完整公式和 JSON 模型项：因变量、核心项、控制变量、生成项、固定效应、聚类 |
| beta、se、p、direction_match | 当前检验项的系数、标准误、p 值和预期方向匹配；须结合公式与样本解释 |
| 普通 R²、调整 R²、within R²、组内 R²定义、组内 R²吸收项 | 组内 R²为同一估计样本上 1－完整模型 SSE／仅含截距和被吸收固定效应模型 SSE；无固定效应或无法计算时留空，不以普通 R²替代 |
| 样本量（N）、sample_identity、processing_input_n、processing_eligible_n、complete_case_removed_n | 估计行数、实际行身份、处理输入行数、门槛后行数、模型完整案例删除行数 |
| 是否候选模型、strong_pass、weak_pass、是否成功运行、失败原因 | AB 只可能是 candidate；strong／weak 仅为 C 阶段假设级筛查标签，强通过也算弱通过；失败记录仍保留 |

## 七、synthesis 与展示案例怎么使用

synthesis 根据运行清单读取当前批次已启用且被请求的模块的三份机器表，校验数据指纹、公共设定、配置版本、历史快照和表结构；仅目录里“存在文件”不构成准入证据。缺少可核验结果时整合停止。综合表一行对应一个 `specification_id`；是否通过只读取 C 阶段假设级判定，A/B 候选不能替代 C。当前登记的 `required_pass` 默认全为 `none`，用户应按研究方案逐条设为 `strong`／`weak`／`none`。

| result_synthesis/ 中的主要文件／工作表 | 判定口径 |
| --- | --- |
| `merged_full_results`／`full` | 全部已执行公共设定；即使失败、未通过或没有 C 结果也保留 |
| `merged_require_results`／`require` | 逐条满足用户在假设登记中设置的 `required_pass`；全部为 `none` 时不额外设通过门槛 |
| `merged_strong_pass_results`／`strong` | 本轮纳入且启用、已登记的**全部假设**在同一设定下 C 阶段强通过 |
| `merged_weak_pass_results`／`weak` | 上述全部假设在同一设定下 C 阶段至少弱通过；强通过也计入 |
| `hypothesis_status_detail`／`假设明细` | 每个设定、每个纳入假设的强／弱／未通过／运行失败／缺少 C 状态及模型 ID |
| `merged_model_detail_results.csv` | 逐模型／路径的完整长表；保留原始诊断供审计、设定曲线和案例追溯 |

顶层 `综合结果总览.xlsx` 按 `require、full、strong、weak、假设明细、字段说明` 六张工作表排列。四张主表同一表头：`模型合并ID、specification_id、Strong pass、weak_pass、no&lack_pass`，再接样本门槛、处理方案、控制变量组合及明细、聚类设定、运行／候选状态、三类效应的 C 模型 ID 和 `model_ids_json`。`weak_pass` 文本列列出**仅弱通过**假设；强通过列在 `Strong pass`，但在 `weak` 表筛选时仍视作弱通过。`no&lack_pass` 是未通过、失败和缺少 C 的合并提示，三种原因另有独立列。严格表为空仍有表头，请到 `full` 和 `假设明细` 查原因。设定曲线仍基于已执行的逐模型明细，不以综合主表代替回归证据。

合并键不完整的结果可按配置留在完整审计表，但不能成为展示案例。跨模块展示必须有启用的完整理论链，并核对历史模块 YAML 中的变量关系、假设和模型形式；不同样本只记录提示。**零展示案例是正常结果**，不能用旧文件或单条显著路径补齐。启用案例筛选时，先看 display_case_rejections.csv 的拒绝原因，再看 display_case_index.csv／json 的 case_id、模型 ID 和样本差异；启用 dofile_bridge 时，display_case_manifest.json 提供精确模型列表、公共设定、样本差异、预处理与来源快照索引。synthesis 自身不生成 do 文件；另见 [结果复现 skill](../结果复现/复现SKILL.md)，可按 `run_id + specification_id` 从历史机器文件定向生成 do。若启用整合快照，synthesis 的 config_snapshot/<模块名>/ 复制各模块回归时快照，synthesis_input_config.yaml 仅记录整合时读到的全局配置，不能替代历史快照。

查看一条综合结果时，先用主表的 `specification_id` 和各效应 `*_model_ids`／`model_ids_json` 找到对应模块的 `standardized_results.csv`；再用 `specification_index.csv` 核对公式、控制变量、处理方案、N 和 `sample_identity`，用 `hypothesis_results.csv` 核对通过依据及中介所需路径；最后沿 `run_record.json` 核对数据指纹、`preprocessing_definitions.json` 与回归时的 `config_snapshot/`。如案例入选，再以 `case_id` 查 `display_case_manifest.json`。主表“模型合并ID”是本轮展示编号，不可单独作为复现依据；基准检验与 synthesis 不生成 do，独立结果复现 skill 负责定向生成。


## 八、当前能力边界与后续三个 skill

当前版本完成共享预处理、三类效应基准筛查、假设级汇总、同批次整合与可核验案例说明，**尚未构成完整的正式实证研究闭环**。后续计划：

1. **变量构造 skill：**依据参考文章和研究情境给出计算公式、所需原始字段、单位及时间口径、情境化调整建议；用户确认变量定义与数据质量。
2. **结果复现／展示 skill：**从经审核的原始输入和选定设定生成精确/简明 Stata do；支持线性/U 型主效应、线性/曲线调节，以及中介总效应、a 路径和 b/c′ 路径的逐模型复跑。用户亲自运行后，再从实际估计值输出论文三线表。中介间接效应的 Bootstrap 推断仍需另行完成，见 [使用说明](../结果复现/复现SKILL.md)。
3. **数据分析与补充检验 skill：**针对研究问题及已执行结果提出并生成严格非线性、机制确认、稳健性和内生性检验建议与代码，例如 Utest、拐点范围、条件效应图。建议不替代研究者的识别和解释。

目前不强制跨模块或中介链内使用共同观测样本，保留将来切换共同样本的接口；不执行 Bootstrap 或完整 U 型确认，不保证联合显著案例，也不宣称穷尽全部合理预设。
